# Tenant Kanban

Kanban is available under `/kanban`. Tenant members with Kanban permissions and the tenant owner can use it; staff/superuser status alone does not grant access to another tenant's boards. Workspace administrators can also invite active system users to individual boards. These guests have Kanban access only to the boards they join and do not become tenant members or gain other CMS permissions. There are no permanent-delete endpoints.

Create a board, customize its columns, then create cards. Drag column headers to reorder and cards to reposition or move between columns. Dropping a card on a board link moves it to that board's first active column. Card ghosts use a card-sized landing placeholder; whole-column ghosts use insertion lines. The board scrolls horizontally and the hovered column scrolls vertically at drag edges. Floating action menus provide arrow buttons and destination selectors as keyboard/touch alternatives. Card links and UUIDs never change on moves; readable `TASK-N` numbers are unique within each tenant. Archive retains descendants and attachments. Use the archive filter to find and restore boards, columns and cards, or undo a recent archive/move from activity. Undo fails safely after a conflicting later change.

Card details open as a large overlay above their board, including on direct card URLs. The left pane shows the title, compact contextual tools, members and a formatted description with an explicit Edit action; the right pane places the comment composer above comments and activity. Labels, dates, checklists and uploads open from the toolbar. On mobile these panes stack in one scrolling overlay. Close/Escape returns to the board and restores focus; unsaved edits/comments keep the overlay open with inline continue/discard actions. Descriptions/comments store Markdown; the visual editor supports headings, emphasis, lists, links, images, quotations and code. Use the mention selector to insert `[@Name](#member-123)`. Mentions, assignments and deadlines produce in-app notifications. Deadline checks run every minute and notify once within the day before the deadline (also immediately when assigned within that window). No email is sent.

## Quick card actions

The card menu opens the card, edits labels/assignees/deadlines, chooses a palette cover color, moves, copies, copies a link, mirrors or archives the card. Copies preserve content, checklist, labels, assignees and cover, but leave comments/files on the original. Mirrors have independent placement/archive state and share editable content with their canonical original. Their open/edit links lead to the original discussion and files; changing the original updates mirrors in the same tenant transaction. Assignment and deadline notifications come from the original only. Copy/mirror creation can be undone by archiving the new card from activity. Column menus add cards, rename, copy a list, reorder and archive optional lists.

## Attachments and import

The board action menu opens Members and Edit board dialogs. Workspace administrators can select any active system user as a board member. An outside user's membership grants access only to the selected board within Kanban; removing them from their last board revokes that access immediately. Existing workspace membership is independent of board membership. Users with access to multiple workspaces can choose one from Profile; selecting a board guest workspace does not grant other CMS permissions. Other users can view the member list but cannot change it. Edit board changes its name and uploads or removes a private background image. Board backgrounds and card covers accept JPEG, PNG, GIF or WebP up to 10 MiB. Card covers are card attachments and use the existing private download ticket.

Users with the workspace `ai.use` permission can generate either image from a prompt or explicitly from board/card content. Board generation sends its title, active list names and up to 30 active card titles; card generation sends its title, the first 2,500 description characters and up to eight checklist items. These inputs go to OpenAI using the existing `OPENAI_API_KEY`; generation is limited to five requests per user per day. When the key or provider is unavailable, generation returns HTTP 503 without exposing provider details.

Uploads go to the existing **private checkpoint bucket**, under `tenants/<tenant UUID>/kanban/`. They are persistent and do not enter the pending-media expiry workflow. The bucket must already be provisioned by the normal checkpoint-storage setup and remain distinct from the public media bucket. Authorized downloads stream S3 ranges for the built-in video player, including asynchronous streaming under ASGI without buffering the entire response. Signed, 15-minute, read-only browser tickets support JWT logins; every use rechecks membership. Do not log ticket query strings or WebSocket protocol headers.

Existing file validation applies: images 50 MiB, documents/audio 100 MiB, MP4/WebM 500 MiB. Validation scans bounded chunks rather than buffering videos in memory. Unsupported formats, empty files and unsafe content are rejected. SVG is downloaded rather than rendered inline. Video is played natively without transcoding; actual browser codec support still applies. Reverse proxies must permit the advertised upload size if operators choose to expose 500 MiB uploads.

Use **Bilaga** to choose files, or drop files anywhere on the open card to attach them. Dropping into the description editor uploads and inserts images or file links at the drop position, including while editing; the editor's image button opens a file picker and inserts the uploaded image at the cursor. Images in the visual editor can be moved by dragging. Dropping files into the comment pane creates a comment with those attachments. An existing card image can also be dragged into the comment pane to include it in a comment. The attachment list shows uploaded files and offers **Kopiera Markdown-bild** for images. The card no longer shows Media Manager import or approval controls; Media Library and Designer retain their dedicated import flows. Approval remains specific to each immutable attachment and is recorded in activity; a Done column does not imply approval.

Media Library and Designer each have an **Importera från Kanban** panel. Search by card text or filename, inspect source card and approval, then explicitly import a copy. Originals remain on the card and imports record destination, user and timestamp. Media imports require at least one approved taxonomy term selected with the shared classification picker, scoped to the destination namespace and allowed for media files. Native imports send `classification_ids`; legacy `tag_ids` remain a compatibility input. Existing global media content-hash uniqueness is preserved: an existing active copy in the same tenant/namespace may be reused only if the importer can access it under ordinary Media Library rules; its previous classifications are retained and the selected terms are added. Inaccessible destinations and collisions with another namespace, tenant or deleted record are rejected without disclosure or deletion. Designer imports use an existing image slot, image validation (including the Designer's 10 MiB limit), permissions and draft revision checks. Save/discard local Designer edits before importing. Import never publishes the theme.

## Search and background work

Card lists support board, column, assignee, label, mine, deadline and archived filters. Search combines lexical matches with semantic similarity; exact `TASK-N` matches rank first. Card list APIs are paginated (100 default, 500 maximum per page); the board client follows pages. Search returns the best 100 matches. Attachment import search returns the newest 100 matching attachments; narrow the search when necessary.

Embeddings use the existing `OPENAI_API_KEY` and optional `KANBAN_EMBEDDING_MODEL` (default `text-embedding-3-small`, 512 dimensions). Searchable title, description, checklist text, comments and filenames are sent to OpenAI. File contents, OCR and video/audio transcription are excluded. Text is chunked within input limits and combined into a card vector. Arrays and indexed revisions live in PostgreSQL; v1 uses exact cosine ranking within the tenant/filter set, without a new vector service/extension. This is intended for small boards; measure before adopting indexed vector search.

Run the existing Celery worker and beat services. Mutation callbacks enqueue indexing; a once-per-minute repair task retries stale entries (100 per pass) and deduplicates deadline reminders. An old indexing job cannot overwrite a newer revision. Lexical search continues when OpenAI/indexing is unavailable. The UI uses Channels invalidations with reconnect and a periodic workspace refresh. Development WebSockets honor the existing `VITE_WS_URL` setting. All Kanban caches and browser tickets are isolated by tenant and authenticated user, including the embedded import panels.

## API contract

All endpoints are under `/api/v1/kanban/`, use the existing authentication and tenant-selection contract, and return camelCase JSON. Python serializers/services own snake_case names; `frontend/src/api/kanban.js` bridges the boundary explicitly. Multipart uploads use `file`, `revision` and optional `comment`.

- `boards/`: GET list, POST `{title}`; `boards/<uuid>/`: GET detail, PATCH `{revision,title?,archived?}`.
- `boards/<uuid>/columns/`: POST `{revision,title}`; `reorder-columns/`: POST `{revision,columnIds}` including every column exactly once.
- `boards/<uuid>/available-members/`: GET candidates; `members/`: POST `{revision,members}`. Changing membership requires `tenant.admin`; outside users gain only selected-board Kanban access.
- `boards/<uuid>/background/`: authenticated GET, multipart POST `{revision,file}` or DELETE `{revision}`; `generate-background/`: POST `{revision,prompt}` or `{revision,fromContent:true}`.
- `columns/<uuid>/duplicate/`: POST `{revision}`; atomically copies the list and active cards in the same board. Required list roles are not copied.
- `columns/<uuid>/`: PATCH `{revision,title?,archived?}`.
- `cards/`: paginated GET and POST `{title,column,...}`. `cards/<uuid>/`: GET detail and PATCH `{revision,...}`. Editable fields: title, description, checklist (`id,text,done`), externalReferences (`system,issueId,url`), assignees (user IDs), labels (label UUIDs), deadline (ISO timestamp/null), coverColor (empty, slate, red, amber, green, blue or purple), archived, column and position. Read-only mirrorOf/contentRevision identify the canonical content and revision; edits to shared mirror content must target that canonical card.
- `cards/<uuid>/duplicate/`: POST `{revision,column,mirror?}`; creates an independent copy or a linked mirror in an active destination inside the tenant.
- `cards/<uuid>/comments/`: POST `{revision,body}` using the card revision; `comments/<uuid>/`: PATCH `{revision,body}` using the comment revision.
- `cards/<uuid>/attachments/`: multipart POST; `attachments/`: GET search (`q`, optional `approved=true`); `attachments/<uuid>/download/`: GET with byte ranges.
- `cards/<uuid>/generate-cover/`: POST `{revision,prompt}` or `{revision,fromContent:true}`; creates a private image attachment and sets it as the cover. `cards/<uuid>/` also accepts `coverAttachment` (image attachment UUID/null).
- `attachments/<uuid>/approve/`: POST `{revision}` using the card revision; `import/`: POST `{revision,destination,...}`. Media requires namespace and tagIds; Designer requires themeId, assetKey and draftVersion, with optional targetBreakpoint.
- `workspace/`: GET members/boards/columns/labels/notifications/upload policy; `workspace/access/`: GET ephemeral browser read ticket; `labels/`: POST `{name}`; `activity/`: GET with optional board; `undo/`: POST `{activityId}`; `read-notification/`: POST `{id}`.

Updates require a current revision and return HTTP 409 on conflict. State and activity commit together. Card placement serializes tenant writes and advances revisions for affected neighbors. Import first spools and validates the source in bounded chunks outside the tenant write lock, then rechecks approval and revision under the lock. Imports hold the tenant write lock while completing the destination copy, so large imports can briefly delay edits in that tenant. No imported or original files are deleted by archive/undo.

Machine API keys can use `kanban.read` and `kanban.write`. Their principal must still belong to the selected tenant, and their existing tenant restrictions apply. Imports additionally require `media.write` or `theme.write`, unless the key has server full access. Browser tickets never authorize writes.

## Local verification

- `scripts/test-kanban.sh`: disposable PostgreSQL on OrbStack, with an internal network and no published ports; tests clean install, upgrade with existing tenant data, concurrent writes, membership revocation, ranges, private uploads, import/provenance, notifications, semantic fallback and related existing scope mappings. Requires the existing `eceee-v4-backend-editor:latest` image; override only its name via `ECEEE_KANBAN_TEST_IMAGE` if needed.
- `cd frontend && npx vitest run src/components/kanban src/api/kanban.test.js`.
- Start the frontend on a registered port, then `PLAYWRIGHT_BASE_URL=http://127.0.0.1:<port> npx playwright test --config playwright.kanban.config.js`. Browser tests use mocked API responses with the real page/editor and capture desktop/mobile/light/dark screenshots. They do not prove live S3/OpenAI availability.
- Run focused ESLint, `npm run build`, backend Black/Flake8 and specs validation before pushing.

The additive initial migration creates only new Kanban tables/indexes/constraints. It does not rewrite existing tenant/content/media data. Back up new Kanban tables and include the private bucket in the existing backup policy before production adoption. No production deployment is part of this change.
